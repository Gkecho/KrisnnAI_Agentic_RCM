# A6 Claim Submission & Response Agent

- **Phase:** MVP; **release:** Wave 1 (A5, A6, A7, A8, A14); **milestone:** M10
- **Build status:** Response side built in M10, shadow mode only (`krisnnai/agents/a6_submission/`, migration 0007, `krisnnai a6 seed|replay`). The release side (submitting claims A5 has cleared) is not built: there is no release signal yet. The engine's clearinghouse stub records and never sends.
- **Spec status:** Draft on the strategy's Appendix A (24 fields). Fields the strategy does not state are marked TBD for the owners named in the strategy; thresholds stay TBD until fixed from baseline data before shadow results are reviewed.
- **Engine support (built, M6):** policy table (default allowed, L0, shadow), decision records, idempotency, point-in-time replay, approval queue service, disabled/stub adapters.

## 1. Business outcome and KPI

Submission acceptance; rejection turnaround.

## 2. Trigger event(s)

Claim approved for release.

## 3. Required data and source systems

837 claims, 999 and 277CA acknowledgements, provider master, clearinghouse connection (partner API).

## 4. Deterministic rules and payer/client policy inputs

Plain code, no model (rule 6). Triggers are decided from the event payload: a 277CA with status category A3 (returned) or A4 (not found), and a 999
with transaction status R (rejected) or E (accepted with errors). A 999 covers a transaction set, so the proposal names every claim whose 837 event
shares the acknowledged GS06 and ST02. Routing is a tenant table (`rejection_route`), seeded as placeholders awaiting sign-off:

| Source | Status | Kind | Category |
|---|---|---|---|
| 999 | R | **technical** | edi_structure |
| 999 | E | business | accepted_with_errors |
| 277CA | A3 / code 21 | business | missing_or_invalid_information |
| 277CA | A3 / any other | business | returned_unprocessable |
| 277CA | A4 | business | claim_not_found |

A status with no row is business and flagged `unrouted`. Only a 999 rejection is seeded as technical; more technical rows need sign-off.
Rules: `rejection_routed`, `claim_matched`, `packet_unchanged` (the packet's codes, diagnoses, units, charges and frequency code equal what is stored),
`within_filing_limit` (A5's `payer_filing_window`, default 365 days), `amount_priced` (A15 pricing for a 277CA; billed charges for a 999, which can cover many claims).
**Likely causes** are the failed rules from A5's pre-release checks on the rejected claim (required fields, duplicate, filing, NCCI, MUE).
Priority = dollars x urgency (urgency 2 within 60 days of the filing limit, else 1); `fix_by` = rejection date + 3 days. All placeholders for sign-off.

## 5. AI task(s) and approved model(s)

Interpreting rejection messages. No model is approved yet; the engine's stub provider is the default and a real provider needs an approved BAA (strategy Decision 6).

## 6. Action options and prohibited actions

**Built actions** (tasks and reviews for a person): `a6_resubmit_review` (technical rejection; a person approves a prepared packet; the only action that could ever
reach the clearinghouse adapter, L3 at most) and `a6_rejection_task` (business rejection; the owner fixes the cause). The **resubmission packet** is the claim
copied verbatim (codes, modifiers, diagnoses, units, charges, frequency code) with an empty `edits` list; it is not an X12 file (no 837 writer yet). A rejected claim
never reached adjudication, so it is resubmitted as a corrected original, not a replacement (frequency 7), which is for claims the payer already accepted. Every proposal
carries the standard inbox card. A live L3 policy was tested end to end: the proposal waits for a named approval, then only the clearinghouse stub records it ("not sent").

Builds corrected/replacement 837s and submits them through the partner clearinghouse, validates acknowledgements, interprets 999/277CA, auto-corrects technical rejections, opens exceptions when business judgement is required. Prohibited for every agent: any change to CPT, ICD-10 or modifiers, any write-off or refund, and any submission to a payer without a named human approval; submission only through the partner clearinghouse adapter; PM/EHR write-back limited to tasks and notes until each action type is approved under strategy Decision 8.

## 18. Point-in-time replay method and label double-review process

The engine's replay harness (built, M6) runs the agent over history using only data known at each event's time; later corrections are excluded or flagged. Gold-standard labels are double-reviewed, agreement is measured, disagreements are adjudicated by the RCM domain lead, and the labeling guideline is versioned (strategy 11B). Gold set and guideline: TBD.
