# A2 Authorization Intelligence Agent

- **Phase:** MVP+; **release:** Wave 3 (A9, A2, A11); **milestone:** M16
- **Build status:** Built in M16, shadow mode only (`krisnnai/agents/a2_authorization/`, `krisnnai a2 seed|sweep|replay`). Reads a new authorization feed (`prior_authorization`, `auth_requirement` tables, migration 0011). Authorization denials (CARC 197/198) are still routed by A8 to the front desk.
- **Spec status:** Draft on the strategy's Appendix A (24 fields). Fields the strategy does not state are marked TBD for the owners named in the strategy; thresholds stay TBD until fixed from baseline data before shadow results are reviewed.
- **Engine support (built, M6):** policy table (default allowed, L0, shadow), decision records, idempotency, point-in-time replay, approval queue service, disabled/stub adapters.

## 1. Business outcome and KPI

Authorization turnaround; auth-related denials.

## 2. Trigger event(s)

Order/service requires authorization, or units are running low.

## 3. Required data and source systems

Orders, authorization requests/responses and unit balances, payer authorization rules, clinical documentation. Not in the repo yet.

## 4. Deterministic rules and payer/client policy inputs

Plain code in `rules.check`, judged as of the checkpoint (7 and 2 days before a booked visit whose payer + CPT is in `auth_requirement`). A request, decision
or unit count dated after the checkpoint does not exist yet. The authorization used is the one linked to the appointment (`appointment_id`), else one whose approved
window holds the visit date. Placeholders for sign-off:
- `no_authorization`: required and none requested. `authorization_denied`: the payer denied it.
- `expired_authorization`: the visit is outside the approved window. `units_exhausted`: units used reached units approved, as of the date the count was true.
- `pending_late`: requested 7 or more days ago, still undecided, visit within 7 days.
Requirements are placeholder payer + CPT rows (`a2 seed`), not payer policy.

## 5. AI task(s) and approved model(s)

Predicting approval risk; checking clinical completeness. No model is approved yet; the engine's stub provider is the default and a real provider needs an approved BAA (strategy Decision 6).

## 6. Action options and prohibited actions

**Built actions (tasks and reviews only, owner front desk):** `a2_auth_request_task` (none requested, or a pending request to chase) and
`a2_auth_exception_review` (denied, expired or units exhausted; the practice manager decides to reschedule, appeal, request again or proceed). Not built: the
packet, clinical completeness check, approval-risk prediction, portal status checks. Original text: Determines auth need, builds the packet, checks missing clinical elements, predicts approval risk, tracks units/expiry, drafts status follow-up. Prohibited for every agent: any change to CPT, ICD-10 or modifiers, any write-off or refund, and any submission to a payer without a named human approval; submission only through the partner clearinghouse adapter; PM/EHR write-back limited to tasks and notes until each action type is approved under strategy Decision 8.

## 13. Shadow-mode evaluation dataset and acceptance criteria

Dataset and acceptance criteria are fixed before shadow results are reviewed: TBD at spec review.

**Synthea mini book (1,500 claims, `--eligibility --authorization`):** 398 appointments needing authorization, 66 with a gap; every planted defect was found
and nothing else (no authorization, expired, pending late, units exhausted), every planted lapse was a CARC 197 denial and was flagged before the visit, request-to-decision
turnaround median 4 days. **Real Synthea run (300 patients):** only 17 appointments carry a CPT in the placeholder requirement set (the SNOMED to CPT crosswalk maps
few procedures), 2 planted defects, both found; too small to say more. One design finding: the first version matched an authorization to a patient + payer + CPT, so
an earlier visit's authorization hid a missing one; the feed now carries `appointment_id` and a visit is judged on its own authorization. The authorizations and
defects are simulated by the same team that wrote the rules.

## 18. Point-in-time replay method and label double-review process

The engine's replay harness (built, M6) runs the agent over history using only data known at each event's time; later corrections are excluded or flagged. Gold-standard labels are double-reviewed, agreement is measured, disagreements are adjudicated by the RCM domain lead, and the labeling guideline is versioned (strategy 11B).
