# A9 Denial Prevention Learning Agent

- **Phase:** MVP+; **release:** Wave 3 (A9, A2, A11); **milestone:** M15
- **Build status:** Built in M15, shadow mode only (`krisnai/agents/a9_learning/`, `krisnai a9 sweep|replay|approve|reject|forward|attribution`). One rule family (payer + CPT + CARC). An approved rule is read by A5 as `learned_pattern`.
- **Spec status:** Draft on the strategy's Appendix A (24 fields). Fields the strategy does not state are marked TBD for the owners named in the strategy; thresholds stay TBD until fixed from baseline data before shadow results are reviewed.
- **Engine support (built, M6):** policy table (default allowed, L0, shadow), decision records, idempotency, point-in-time replay, approval queue service, disabled/stub adapters.

## 1. Business outcome and KPI

Preventable denial recurrence.

## 2. Trigger event(s)

Confirmed denial outcome or recurring defect.

## 3. Required data and source systems

Root causes, user corrections and payment outcomes from A8/A7 (outcome history from Waves 1-2); attribution engine.

## 4. Deterministic rules and payer/client policy inputs

Plain code. Claim outcomes are rebuilt as of a date from the events known by then; a cluster is payer + CPT + CARC over claims the payer answered in the last 120
days. It qualifies at 5 denied claims and a 30% denial rate (placeholders). A weaker cluster that shares 80% of its denied claims with a stronger one for the same payer
and CARC is dropped (one defect, one rule). Coverage: if A5 had already flagged 80% of the cluster's claims before release, no new rule is proposed. In-sample metrics on
the proposal: denial rate, recall (share of that payer's denials with that CARC the rule would have flagged), expected payment denied. A rule has effect only after a named
person runs `a9 approve --rule KEY --by NAME`; A5 then fails claims matching an approved rule with `learned_pattern` (a fix task for billing). `a9 forward` tests each
rule on claims filed after it was proposed; `a9 attribution` links each denial to the upstream agent (A1, A2, A3, A5) that had flagged it, or none.

## 5. AI task(s) and approved model(s)

Clustering causes; proposing rules. No model is approved yet; the engine's stub provider is the default and a real provider needs an approved BAA (strategy Decision 6).

## 6. Action options and prohibited actions

**Built action (review only, owner practice manager):** `a9_rule_proposal_review`. The sweeper raises one `denial.pattern_found` event per new cluster. Not built: clustering
on diagnosis, modifier, provider or free text; model-written explanations. Original text: Clusters causes, links a downstream denial to the upstream process event, proposes new front-end rules, tests their impact in shadow mode, promotes approved rules. Prohibited for every agent: any change to CPT, ICD-10 or modifiers, any write-off or refund, and any submission to a payer without a named human approval; submission only through the partner clearinghouse adapter; PM/EHR write-back limited to tasks and notes until each action type is approved under strategy Decision 8.

## 13. Shadow-mode evaluation dataset and acceptance criteria

Dataset and acceptance criteria are fixed before shadow results are reviewed: TBD at spec review.

**Real Synthea book (2026-10-14, 300 patients, seed 7; a planted pattern: SYNANTHEM denies CPT 99213 with CARC 16 at 60% from 2026-01-01):** exactly one proposal,
SYNANTHEM|99213|16: 6 of 16 claims denied (38% in the window when proposed), recall 100%, A5 had flagged none, 502.20 denied. After `approve`, A5 flagged 83 claims
with `learned_pattern`; the forward test on later claims flagged 24 and hit 11 (precision 46%, recall 100%, 910.80 would have been held). Attribution over 226 denials:
40 had an A1 flag, 58 an A3 flag, 46 an A5 flag, 104 had no upstream flag (counted once per flagging agent). Two findings on the way: the first version measured the rate over
all history, so a recent change was diluted for months (now a 120-day window), and re-running A5 after an approval adds new decision records beside the old ones rather
than replacing them (records are append-only). The pattern is planted by the same team that wrote the rule.
