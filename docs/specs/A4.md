# A4 Coding & Charge Integrity Copilot

- **Phase:** Phase 2; **release:** After the 180-day plan; **milestone:** M18
- **Build status:** Later (Phase 2).
- **Spec status:** Draft on the strategy's Appendix A (24 fields). Fields the strategy does not state are marked TBD for the owners named in the strategy; thresholds stay TBD until fixed from baseline data before shadow results are reviewed.
- **Engine support (built, M6):** policy table (default allowed, L0, shadow), decision records, idempotency, point-in-time replay, approval queue service, disabled/stub adapters.

## 1. Business outcome and KPI

Coder productivity; coding denials; audit variance.

## 2. Trigger event(s)

Note signed or charge ready.

## 3. Required data and source systems

Signed notes, charge candidates, NCCI/MUE tables, diagnosis codes. Not in the repo yet.

## 4. Deterministic rules and payer/client policy inputs

Payer and client policy inputs: TBD at spec review.

## 5. AI task(s) and approved model(s)

Suggesting codes and modifiers from documentation. No model is approved yet; the engine's stub provider is the default and a real provider needs an approved BAA (strategy Decision 6).

## 6. Action options and prohibited actions

Suggests codes, modifiers and charge candidates; checks NCCI/MUE logic, diagnosis-code consistency, documentation support and outliers; highlights uncertainty. Prohibited for every agent: any change to CPT, ICD-10 or modifiers, any write-off or refund, and any submission to a payer without a named human approval; submission only through the partner clearinghouse adapter; PM/EHR write-back limited to tasks and notes until each action type is approved under strategy Decision 8.

## 7. Confidence/materiality thresholds

Thresholds are set per action type from the signed-off baseline and shadow evidence, not stated here (strategy Section 6): TBD at spec review.

## 8. Human approval role and SLA

Coder approval for coding decisions. SLA: TBD.

## 9. Execution adapter and retry/idempotency behavior

Engine idempotency key (tenant, event, agent, action type): a repeat run returns the existing record and executes nothing (built, M6). This agent's adapter, retry policy and duplicate-action prevention: TBD.

## 10. Verification condition and evidence of success

What evidence proves the action succeeded: TBD at spec review.

## 11. Failure/exception path

Fallback queue when any API/portal/model dependency fails (strategy Section 8); exception path for this agent: TBD at spec review.

## 12. Audit fields and retained artifacts

The engine's decision record on every run (built, M6): agent id and version, event and trigger, input snapshot with source lineage, rules fired, model id/version and prompt hash, confidence, materiality, proposed action and payload, autonomy level, mode, approver and time, execution result, verification condition and result. Write-back also keeps before/after values and source evidence (strategy Section 8). Retention and minimization policy: TBD with Compliance.

## 13. Shadow-mode evaluation dataset and acceptance criteria

Dataset and acceptance criteria are fixed before shadow results are reviewed: TBD at spec review.

## 14. Production quality metrics and drift thresholds

Drift, false-positive, false-negative and user-override monitoring (strategy Section 8). Metrics and thresholds: TBD.

## 15. Outcome attribution method and financial reporting rule

Distinguish detected, worked, submitted, accepted, paid and incremental recovered; incrementality only against a control (strategy Section 4). Financial reporting rule for this agent: TBD.

## 16. Identity/matching dependencies and data-quality gates

Depends on identity resolution across systems and claim/remit/payment matching (matching built, M3; cross-system identity resolution not built). Data-quality gates: G0 reconciliation within a tolerance agreed in writing with the partner.

## 17. Thresholds, sample sizes and decision rule fixed before shadow results are reviewed (value, owner, date)

Metrics, thresholds, sample sizes and the decision rule must be recorded and ratified before shadow results are viewed. Value, owner, date: TBD at spec review.

## 18. Point-in-time replay method and label double-review process

The engine's replay harness (built, M6) runs the agent over history using only data known at each event's time; later corrections are excluded or flagged. Gold-standard labels are double-reviewed, agreement is measured, disagreements are adjudicated by the RCM domain lead, and the labeling guideline is versioned (strategy 11B). Gold set and guideline: TBD.

Signed record and stop criteria for this agent: TBD. A failed gate holds or demotes the action.
