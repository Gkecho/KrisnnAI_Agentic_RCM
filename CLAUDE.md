# KrisnnAI RCM — rules for Claude Code

KrisnnAI RCM is an intelligence layer that sits above a medical practice's PM/EHR and clearinghouse. It reads claim data (837, 835, 999, 277CA, PM tables), finds revenue problems, and runs agents that rank, prepare and (only after proven gates) execute RCM work.

Strategy source: `docs/strategy_v5.docx` (internal). Build order: `docs/BUILD_PLAN.md`. Follow the plan one milestone at a time.

## Stack (change only with an ADR in docs/adr/)
- Python 3.12, FastAPI for APIs, SQLAlchemy 2 + Alembic for SQL Server (pyodbc).
- pytest for tests. ruff for lint. Type hints everywhere.
- Background work: simple `job` table + worker process until ADR-0003 decides on a durable workflow engine.
- Config via environment variables; no secrets in the repo.

## Hard rules (never break these)
1. **No real PHI in the repo, tests, logs, prompts or commits.** Use synthetic data generated by `tests/fixtures/make_synthetic.py`. Patient identifiers are stored as a salted hash reference, never raw names/DOB/member IDs in logs.
2. **Read-only toward client systems.** No code may write to a client PM/EHR database. MVP write-back is limited to tasks and notes, and only through an adapter that is disabled by default and gated by policy.
3. **Never submit to payers directly.** Claim submission/resubmission goes only through the partner clearinghouse adapter, and only for actions whose policy allows it.
4. **Codes, refunds and write-offs are never automatic.** No agent may change CPT, ICD-10, modifiers, or create write-offs/refunds without a named human approval.
5. **Every agent decision writes a decision record** (see below). No record, no action.
6. **Rules first, AI second.** Deterministic checks (payer rules, deadlines, contract math, required fields, duplicates) are plain code. Use a model only for extraction, classification, prediction or drafting, behind `engine/models.py` (model abstraction). No PHI goes to any model endpoint without an approved BAA; default model provider is a stub.
7. **Idempotency.** Ingesting the same file twice, or re-running an agent on the same event, must not create duplicates. Key on file hash and X12 control numbers (ISA13/GS06/ST02), and on (tenant_id, event_id, agent, action_type).
8. **Tenant isolation.** Every table has `tenant_id`; every query filters by it. Tests must include a cross-tenant leak test.
9. **Point-in-time correctness.** Anything used for replay or evaluation must be computable "as of" a timestamp, using only data known then. No future leakage.
10. **Money is Decimal**, never float. Dates are dates, not strings.

## Decision record (engine/decision_record.py)
Each agent run on an event stores: tenant_id, agent_id, agent_version, event_id + trigger type, input snapshot reference with source lineage, rules fired (id + result), model id/version + prompt hash (if used), confidence, financial materiality ($), proposed action type + payload, autonomy level applied (L0–L4), mode (shadow/live), approver + time (if any), execution result, verification condition + result, created_at.

## Autonomy levels (policy per tenant + action type)
L0 observe · L1 assist (rank/explain) · L2 prepare (draft for review) · L3 approve-and-run (named approval) · L4 bounded autonomous (client caps). Default for every new action type is L0/shadow. Promotion is a config change backed by evidence, never a code default.

## How to work
- Start each milestone in plan mode: restate the goal, list files to create/change, and the tests that prove "done". Wait for approval.
- Small commits, one concern each. Tests pass before moving on.
- When a requirement is unclear or touches RCM domain rules, stop and ask Gk rather than guess. Record decisions in `docs/adr/`.
- Keep SQL readable; Gk is a SQL Server developer and will review it.
